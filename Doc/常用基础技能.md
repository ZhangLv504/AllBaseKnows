# .gitignore规则总结

`.gitignore` 文件用于告诉 Git 哪些文件或目录应当被忽略，不纳入版本控制。语法结构简洁，遵循自上而下的匹配策略。

### 一、 核心语法规则总结

#### 1. 基础匹配

- **`filename.ext`**：忽略项目任意子目录下名为 `filename.ext` 的文件。
- **`dir_name/`**：末尾带斜杠 `/` 表示只忽略名为 `dir_name` 的**目录**（及其内部所有内容）。
- **`filename`**：无斜杠时，同时忽略匹配该名称的**文件和目录**。

#### 2. 通配符（Glob 模式）

- **`\*`**：匹配零个或多个除路径分隔符 `/` 以外的字符。
    - `*.log`：忽略所有 `.log` 结尾的文件。
- **`?`**：匹配单个除 `/` 以外的字符。
    - `file?.txt`：匹配 `file1.txt`，但不匹配 `file10.txt`。
- **`[]`**：匹配方括号内的任意单个字符。
    - `[a-z].txt`：匹配 `a.txt` 到 `z.txt`。
- **`\**`**：跨层级匹配目录。
    - `**/logs/`：忽略任意层级下的 `logs` 目录（如 `logs/`, `src/logs/`）。
    - `docs/**/*.pdf`：忽略 `docs/` 及其所有子目录下的 `.pdf` 文件。

#### 3. 路径限定与反向规则

- **`/prefix`**：以斜杠 `/` 开头表示**仅匹配项目根目录**下的文件/目录，不影响子目录。
    - `/build`：仅忽略根目录下的 `build`，不忽略 `src/build`。
- **`!`（反向匹配/例外规则）**：排除忽略，即重新包含某个文件或目录。
    - `*.log` 结合 `!important.log`：忽略所有 `.log` 文件，但保留 `important.log`。

> **注意（常见陷阱）**：如果某个父目录已经被忽略，Git 出于性能考虑不会递归检查该目录，此时**无法**通过 `!` 重新包含该父目录中的子文件。
>
> - **错误示例**：
>
>     代码段
>
>     ```
>     logs/
>     !logs/important.log   # 不生效！因为 logs/ 已经被完整忽略
>     ```
>
> - **正确写法**：
>
>     代码段
>
>     ```
>     logs/*
>     !logs/important.log   # 生效：仅忽略 logs 下的内容，而非屏蔽整个目录
>     ```

### 二、 规则匹配优先级

当一条路径同时匹配多条 `.gitignore` 规则时，优先执行策略如下：

1. **后声明覆盖先声明**：同一文件被多次配置时，文件靠下的规则会覆盖靠上的规则。
2. **绝对路径高于通配路径**：具体的精确路径优先于通配符匹配。
3. **否定规则（`!`）高于常规忽略**：如果未被父级目录屏蔽，`!` 会强制包含该文件。

### 四、 常见问题与运维技巧

#### 1. `.gitignore` 对已追踪（Tracked）的文件无效

如果文件在加入 `.gitignore` 之前已经被 `git add` 或 commit 过，后续修改 `.gitignore` 将不会对其生效。

- **解决方法**：将文件从 Git 索引中移除（保留本地文件）：

    ```Bash
    git rm --cached <file-path>
    # 若要清除整个被忽略的目录：
    git rm -r --cached <dir-path>
    ```

#### 2. 检查某条路径被哪条规则忽略

当出现意料之外的忽略行为时，使用以下命令排查定位：

```Bash
git check-ignore -v <path/to/file>
```



# CMake 常用配置

### 1. `add_library(protocol STATIC src/*.cpp)`

- **基本作用**：定义一个名为 `protocol` 的**静态链接库**目标（Linux 下生成 `.a`，Windows 下生成 `.lib`）。

- **底层机制**：告诉 CMake 将 `src/` 目录下匹配到的源文件编译成目标文件（`.o` / `.obj`），并打包归档为静态库。

- **潜在风险提示**：在 CMake 中直接使用 `src/*.cpp` 通配符（Globbing）是不推荐的做法。如果在该目录下新增或删除了 `.cpp` 文件，CMake 无法自动感知变更，可能导致编译时漏掉新文件，除非手动重新运行 `cmake` 配置。建议明确列出源文件路径，或配合 `CONFIGURE_DEPENDS` 使用：

    CMake

    ```CMake
    file(GLOB_RECURSE PROTOCOL_SRCS src/*.cpp)
    add_library(protocol STATIC ${PROTOCOL_SRCS})
    ```

### 2. `target_include_directories(protocol PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)`

- **基本作用**：为 `protocol` 库添加头文件搜索路径（-I 目录）。

- **核心在于 `PUBLIC` 关键字**：

    - **对自己（protocol）**：在编译 `protocol` 内部的 `.cpp` 时，允许 `#include` 该目录下的头文件。
    - **对链接方（依赖 protocol 的可执行程序或其它库）**：传递该头文件路径。任何通过 `target_link_libraries(myapp PRIVATE protocol)` 链接了 `protocol` 的目标，都会**自动继承**这个头文件搜索路径，无需在 `myapp` 里重复写 `target_include_directories`。

- **细节纠错**：代码中写成了 `${CMAKE_CURRENT_SOURCE_DIR} /include`（空格及路径拼接），这会导致 CMake 将其识别为两个单独的参数（`.../dir` 和 `/include`），引发路径找不到或查找根目录 `/include` 的异常。正确写法应去掉中间的空格：

    CMake

    ```CMake
    target_include_directories(protocol PUBLIC 
        ${CMAKE_CURRENT_SOURCE_DIR}/include
    )
    ```

### 3. `target_compile_features(protocol PUBLIC cxx_std_17)`

- **基本作用**：为 `protocol` 声明 C++17 标准的语言特性需求。
- **核心在于 `PUBLIC` 传递与契约**：
    - **对自己**：强制 CMake 在编译 `protocol` 自身的源码时开启 C++17 编译器标志（如 `-std=c++17` 或 `/std:c++17`）。
    - **对链接方**：传递标准需求。如果外层调用方（如 Client 或 Server 可执行文件）链接了 `protocol`，CMake 会自动确保调用方也以**不低于 C++17** 的标准去编译。这保证了如果 `protocol/xxx.h` 中使用了 C++17 特性（如 `std::optional`、`std::variant` 或结构化绑定），外层包含该头文件时不会因为 C++ 标准太低而报错。

### 综合优化后的 CMake 片段

修正了路径空格与 Glob 问题后的规范写法：

```CMake
# 1. 明确声明静态库 target
add_library(protocol STATIC
    src/protocol_encoder.cpp
    src/protocol_decoder.cpp
)

# 2. 导出头文件路径（PUBLIC 自动传递给链接方）
target_include_directories(protocol PUBLIC 
    ${CMAKE_CURRENT_SOURCE_DIR}/include
)

# 3. 绑定并传递 C++17 标准需求
target_compile_features(protocol PUBLIC cxx_std_17)
```



# git推送到远端整体流程命令

1. **查看当前状态（推荐操作）** 了解当前本地仓库中有哪些文件被修改、新建或删除。

```Bash
git status
```

1. **将改动添加到暂存区** 将工作区中所有的改动（包括新增、修改、删除的文件）提交到暂存区备用。

```Bash
git add .
```

*(注：如果只想提交特定文件，可以使用 `git add 文件名`)*

1. **提交到本地仓库** 将暂存区的内容正式生成一次提交记录，并附带本次更改的说明。

```Bash
git commit -m "此处填写提交说明，例如：修复登录Bug"
```

1. **关联远程仓库（仅限首次推送时需要）** 如果这是一个全新的本地项目，还没有连接到云端仓库，需要配置远程地址。如果已经克隆或关联过，直接跳过此步。

```Bash
git remote add origin <你的远程仓库URL>
```

1. **拉取远端最新代码（多人协作时必备）** 为了防止覆盖他人的代码或产生冲突，推送前通常需要先拉取远程的最新改动并与本地合并。如果远端是空仓库则无需这一步。

```Bash
git pull origin <分支名>
```

1. **推送到远程仓库** 将本地的提交记录推送到远端服务器。如果是第一次推送当前分支，需要加上 `-u` 参数来建立本地与远程分支的追踪关系。

```Bash
# 首次推送当前分支（以推送到 main 分支为例）
git push -u origin main

# 非首次推送（建立过追踪关系后）
git push
```



# git初始化创建仓库

### 步骤零：一劳永逸（修改 Git 全局默认分支）

在终端里执行下面这句，让以后所有的新项目默认都叫 `main`：

```bash
git config --global init.defaultBranch main
```

### 步骤一：初始化并提交本地代码

```bash
# 1. 初始化本地仓库（因为做了步骤零，现在这里默认就是 main 分支了）
git init

# 2. 将代码添加到暂存区（注意 .gitignore 文件最好先建好，过滤掉 build 等无用文件夹）
git add .

# 3. 提交到本地仓库
git commit -m "Initial commit"
```

### 步骤二：关联远程并拉取（防止冲突）

如果你在 GitHub 网页端创建仓库时，**勾选了添加 `README.md` 或 `.gitignore`**，远程仓库就会有一个初始提交，直接 push 会报错。所以先关联，再拉取：

```bash
# 4. 关联你的 GitHub 仓库
git remote add origin https://github.com/ZhangLv504/AllBaseKnows.git

# 5. 拉取远程 main 分支的代码并合并
#（--allow-unrelated-histories 允许合并没有共同祖先的历史，防止报错）
git pull origin main --allow-unrelated-histories
```

*⚠️ 提示：执行第 5 步时，可能会弹出一个黑色终端界面让你输入合并信息（类似于 Vim）。这时直接按键盘左上角的 `Esc` 键，然后输入 `:wq` 并按回车即可退出。*

### 步骤三：推送到 GitHub

```bash
# 6. 将本地代码推送到远程 main 分支，并建立追踪关系
git push -u origin main
```

执行完这一步，去网页上刷新你的 GitHub 仓库，代码就全部上去了。

------

### 💡 附：如果不想删 `.git`，只想在当前基础上抢救

如果你不想删掉现有的 `.git` 文件夹，直接在你当前终端（显示 `master` 状态）里依次执行这三句：

```bash
# 1. 把本地的 master 重命名为 main
git branch -m master main

# 2. 拉取远程的 main（如果远程创建时生成了 README，必须拉取合并）
git pull origin main --allow-unrelated-histories

# 3. 推送到远程 main
git push -u origin main
```
